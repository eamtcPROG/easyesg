lets this file answer *what is left* without a reader filtering a third of it away first.

The order is the **Stage** sequence below, authored 12 Sep 2026 and **independent of the task
numbers**. `architecture.md` §15.4 is unamended and still describes the nine-step build order the
plan was first sliced from; the archive keeps that mapping in its phase headings. Where
`design/IMPLEMENTATION_PLAN.md`'s UI phases and this Stage order disagree, the Stage order governs
delivery and the implementation plan still governs the UI track's own internal sequence. Tasks are
**vertical slices in build order, not per-application backlogs**: where a feature spans back and
front, the API task comes immediately before its screen task. The **Scope** column names the
workspaces a task touches (`api`, `web`, `admin`, `worker`, `pkg:*`, `infra`, `config`, `docs`,
`root`).

**This is a tracking artifact, not an eighth specification document.** The seven-document set
keeps its precedence: where a task row and a spec identifier disagree, the identifier wins and
this row is what is wrong. Cite decisions by identifier (`FR-…`, `AD-…`, `DR-…`) rather than
restating them.

**Status:** `DONE` · `IN PROGRESS` · `TODO` · `BLOCKED`. Task numbers are stable — cite them in
commits and in [build-log.md](build-log.md), which records *how* each completed task actually
went, deviations included.

**The Status cell holds exactly one of those four words — nothing else, and no date**; when a task
closed is the date on its [build-log.md](build-log.md) entry. A task's status is the roll-up
of the sub-steps listed inside it. The rule, and why it is written down rather than left to convention, is
in the root `CLAUDE.md` beside this file's own entry in the document table.

**A task lives in exactly one of the two plan files, and it moves when its last sub-step closes.**
Closing a sub-step is a two-part edit — mark its item **✓** in the task's Description, write the
build-log entry — and the task **stays here**, because a reader of the active plan needs to see which
parts of an open task are done. Closing the last one closes the task: its Status becomes `DONE` and
its row moves into [archived_tasks.md](archived_tasks.md) under the phase heading it was sliced under. **Zero fully closed groups remain here**, and `pnpm docs:check` refuses one.

**A Stage is an ordering; a task number is an identifier.** Stage numbers are cited nowhere outside
this file and may be re-cut whenever the delivery order changes. Task numbers are cited outside this file (next paragraph but one) and never move. Cite a
task number; never cite a Stage. **Re-cut 6 Oct 2026** (project owner): *Edge, deploy, runbooks* moved last.

**A number is an identifier; only tasks 1–73 are also the order.** Those were sliced together and
each assumes its predecessor. Anything added afterwards is **appended, never inserted**: a task
number is cited in commit messages, in `architecture.md`, in `build-log.md`, in seventy-nine of the eighty migration files and in source comments, so renumbering would falsify every one of them and
leave the stale copies in git history wrong forever. The cost is that the document's order and the
number's order differ — so a row whose position is a dependency statement says so in bold.

**A task too large to close in one go is split into sub-steps, never into new numbers.** Task 25
becomes `25.1`, `25.2`, `25.3`; the numbered row above them keeps its name, its description and its
recorded deferrals **verbatim**, and *task 25* still names the same body of work — so every citation
of it in `CLAUDE.md`, [build-log.md](build-log.md), `config/seed/README.md`, the migrations and some
forty source comments stays true. A sub-step is a **new identifier**, not a renumbering of anything,
which is the only reason the paragraph above permits it.

**One row per task** (compressed 6 Oct 2026, project owner, task 184).  A task is one row, and its
**Description** opens with the task's own text and then lists every sub-step it covers, one per line:
`**60.6** *Name* — what it does → its expected result`. A sub-step that is done carries **✓**, one in
progress or blocked says so in italics, and one scheduled in a later Stage says which. **The sub-step
numbers are kept as labels**, never renumbered, because they are cited in the requirement parts'
Status lines, in `architecture.md` §12.5.6, in migrations and in build-log entries, and each of those
citations still resolves to a line here. A sub-step remains the executable unit — the thing someone
picks up, closes and writes a build-log entry for. **Scope** is the union of the task's own and its
sub-steps'.

**Related documents** lists the specification identifiers the row cites — use cases, screens, UX rules,
NFRs, ADs and DRs, design decisions, the task-182 decisions as `182/n`, and `architecture.md` sections
— read from the row's own text, so it adds nothing the row does not already say. **Covered FR** lists
the requirements whose block, in a `functional_requirements/` part, names this task or one of its
sub-steps in its Status line (`functional_requirements.md` §2.8): it is the inverse of those Status
lines, not a reading of the prose, so a requirement a row merely mentions is not counted as covered.
**Zero rows disagree with that inverse**, and `pnpm docs:check` refuses one that does.

**A task appears once, in the Stage holding its earliest *open* sub-step.** Its closed sub-steps travel
with it, so a task moves forward as its early sub-steps close and a Stage empties when its own work
does. A sub-step scheduled in a later Stage stays listed inside its task and says so — task `54`'s `54.4` … `54.6` and task `62`'s `62.2` and `62.3` are Stage 9's, listed in Stage 3's rows. (Amended 1 Oct 2026, project owner, so a Stage can close while a group it held keeps a later tail.)

**A sub-step may be renumbered while nothing frozen cites it — and the renumbering is recorded.** Amended 25 Aug 2026: the rule above protects *history* — commit messages, migrations, source comments — so a sub-step no such record names may move, its citations in this file fixed in the same edit; task 36's `36.3` … `36.7` moved that way. **The test is what a number is frozen into, not how old it is:** `25.4`, `51.1`, `51.4`, `52.3` and `60.4` are cited in commit `89781d7` and can no longer move, and a sub-step named in a build-log entry never moves again.

**A sub-step is sized to close on its own.** It passes the gates its change reaches and earns its own
build-log entry without waiting for its siblings — that is the whole test. A slice that cannot (a
migration without the use case that reads it, a screen without its API) is not a sub-step but half of
one, and belongs merged with its other half.

**Before starting a task, raise its unknowns in one batch** (CLAUDE.md, "Open questions are not
debt"). A task is not started by writing its first file; it is started by checking what it needs
decided.

**Before closing a sub-step or a task, run the gates its change reaches; before closing a Stage, `pnpm gates:clean`
and the three review agents over the Stage's whole diff** (owner, 6 Oct 2026; CLAUDE.md, "Closing a task"). A Stage
closes when its last row leaves this file. Then write the build-log entry — for a Stage, one of its own: a task whose
reasons are not recorded is not closed, and neither is a Stage.

**Appended 11 Sep 2026, when Advisor portfolio management was promoted out of `use_cases.md` §7.1 into MVP scope as

Numbers are appended and the document's order is not the build order here: **task 116 lands with task 29 and must precede
every other row in this phase**, because the relationship is what the rest reads. Task 117 follows tasks 28 and 83, task 118
follows 83 and 32, task 119 follows 30, task 120 follows 53, 54, 63 and 68 and so is Stage 9's, and task 121 follows 49 … 52.
**What the promotion found, and it is why this phase is small rather than a second tenancy model.** The *provision* was
already MVP and only the *behaviour* was deferred: FR-14 models typed organization relationships expressly so the Advisor
type can be activated without a schema change, and FR-12 already resolves a caller's memberships and owns the switch of
active organization — **specified and scheduled as task 83, which has since closed** (`archived_tasks.md` rows 83, 83.1 … 83.3; `PUT /session/organization` is built), and which the dependency line above made 117 and 118 wait for. What had no row anywhere was the **relationship lifecycle**: a
request that confers nothing, a grant carrying an entity scope and an expiry, a revocation that bites on the next request.
Task 116 is that gap; everything after it is surface over it.
**Nothing here invents a parallel mechanism, and one row exists to prove it.** Entering a client (118.2) is task 83's switch
with membership resolved through a relationship rather than through a membership record — the same route, the same session
shape, the same `@RequiresRole` chain — which is a statement about the switch 83 built (83.1's route, 83.3's step) rather than a new mechanism, and is why 118 follows it. The consolidated board (118.3) reads task 42's roll-up rather than computing a second
one. The plan (120) is task 53's catalogue and task 54's entitlement service with advisor-scoped keys, and D-16 forbids any
of those keys reaching a client organization. The notices (121) are task 49's categories. A slice below that finds itself
needing a second mechanism has found a defect in task 116, not a requirement.
**D-15 is an architectural claim, and 117.2 is where it is tested rather than asserted.** An advisor session resolves to
exactly one tenant, so the RLS predicate and task 12's isolation proof apply unmodified and this phase introduces
**no exception to tenant isolation**. That is the whole distinction from the monitoring domain of Stage 6, promoted on 17 Nov 2026
(`use_cases.md` D-18) — an advisor *enters* organizations one at a time, a monitor *reads across* them, and does so without an
exception because the figures it reads are rows in its own tenant — and it is worth a failing test rather than a paragraph.
