# Tasks

**What is left, in the order it will be delivered.** The closed rows are in
[archived_tasks.md](archived_tasks.md) — 84 numbers and 164 of them — and moving them out is what
lets this file answer *what is left* without a reader filtering a third of it away first.

The order is the **Stage** sequence below, authored 12 Sep 2026 and **independent of the task
numbers**. `architecture.md` §15.4 is unamended and still describes the nine-step build order the
plan was first sliced from; the archive keeps that mapping in its phase headings. Where
`design/IMPLEMENTATION_PLAN.md`'s UI phases and this Stage order disagree, the Stage order governs
delivery and the implementation plan still governs the UI track's own internal sequence. Tasks are
**vertical slices in build order, not per-application backlogs**: where a feature spans back and
front, the API task comes immediately before its screen task. The **Scope** column names the
workspaces a task touches (`api`, `web`, `admin`, `worker`, `pkg:*`, `infra`, `config`, `docs`,
`root`).

**This is a tracking artifact, not an eighth specification document.** The seven-document set
keeps its precedence: where a task row and a spec identifier disagree, the identifier wins and
this row is what is wrong. Cite decisions by identifier (`FR-…`, `AD-…`, `DR-…`) rather than
restating them.

**Status:** `DONE` · `IN PROGRESS` · `TODO` · `BLOCKED`. Task numbers are stable — cite them in
commits and in [build-log.md](build-log.md), which records *how* each completed task actually
went, deviations included.

**The Status cell holds exactly one of those four words — nothing else, and no date**; when a task
closed is the date on its [build-log.md](build-log.md) entry. A parent row's status is the roll-up
of the sub-steps beneath it. The rule, and why it is written down rather than left to convention, is
in the root `CLAUDE.md` beside this file's own entry in the document table.

**A group lives in exactly one of the two plan files, and it moves when its last sub-step closes.**
Closing a sub-step is a two-part edit — set the Status, write the build-log entry — and the row
**stays here**, because a reader of the active plan needs to see which parts of an open task are
done. Closing the last one closes the parent, and then the whole group moves into
[archived_tasks.md](archived_tasks.md) under the phase heading it was sliced under. A group is
never split across the two files: a parent's roll-up would end up in a different file from the rows
it rolls up. **Zero fully closed groups remain here**, and `pnpm docs:check` refuses one.

*(That claim counted `DONE` **rows** until 12 Sep 2026 and was wrong on its second day — task 67.2
closed while its siblings stayed open, which is the ordinary case and which the rule as first
written forbade. Recorded rather than quietly widened, because the original sentence is what a
reader would otherwise still believe.)*

**A Stage is an ordering; a task number is an identifier.** Stage numbers are cited nowhere outside
this file and may be re-cut whenever the delivery order changes. Task numbers are cited in commit
messages, in `architecture.md` §12.5.6, in [build-log.md](build-log.md), in thirty-four of the
thirty-six migration docblocks and in several hundred source comments, and they never move. Cite a
task number; never cite a Stage.

**A number is an identifier; only tasks 1–73 are also the order.** Those were sliced together and
each assumes its predecessor. Anything added afterwards is **appended, never inserted**: a task
number is cited in commit messages, in `architecture.md`, in `build-log.md`, in thirty-four of the
thirty-six migration files and in source comments, so renumbering would falsify every one of them and
leave the stale copies in git history wrong forever. The cost is that the document's order and the
number's order differ — so a row whose position is a dependency statement says so in bold.

**A task too large to close in one go is split into sub-steps, never into new numbers.** Task 25
becomes `25.1`, `25.2`, `25.3`; the numbered row above them keeps its name, its description and its
recorded deferrals **verbatim**, and *task 25* still names the same body of work — so every citation
of it in `CLAUDE.md`, [build-log.md](build-log.md), `config/seed/README.md`, the migrations and some
forty source comments stays true. A sub-step is a **new identifier**, not a renumbering of anything,
which is the only reason the paragraph above permits it.

**Reading a split row.** A **bold number** is a group: its Description and Expected-result columns
are the original row, unchanged, and its Status is the roll-up of the sub-steps below it. A decimal
number is the executable unit — the thing someone picks up, closes, and writes a build-log entry
for. Where a sub-step's Scope differs from its parent's, the row says so and says why.

**A group appears once, in the Stage holding its earliest sub-step, and a later Stage names the
sub-steps it holds in its own intro.** Tasks `67`, `74` and `133` are split across Stages this way.
No row is duplicated, so the roll-up stays single-sourced.

**A sub-step may be renumbered while nothing frozen cites it — and the renumbering is recorded.** Amended 25 Aug 2026, the first time it bit: task 36 went from four module slices to eleven, which shifted `36.3` … `36.7`. The rule above protects *history* — commit messages, migrations, source comments — and none of those named a `36.x`; the only citation was one row in this file, fixed in the same edit. **The test is what a number is frozen into, not how old it is:** `25.4`, `51.1`, `51.4`, `52.3` and `60.4` are cited in commit `89781d7` and can no longer move, and a sub-step named in a build-log entry never moves again.

**A sub-step is sized to close on its own.** It passes the gates its change reaches and earns its own
build-log entry without waiting for its siblings — that is the whole test. A slice that cannot (a
migration without the use case that reads it, a screen without its API) is not a sub-step but half of
one, and belongs merged with its other half.

**Before starting a task, raise its unknowns in one batch** (CLAUDE.md, "Open questions are not
debt"). A task is not started by writing its first file; it is started by checking what it needs
decided.

**Before closing one, run the gates its change reaches; before closing its parent, run
`pnpm gates:clean` and the three review agents** (CLAUDE.md, "Closing a task"). Then write the
build-log entry: a task whose reasons are not recorded is not closed.

## Stage 1 — Identity, authorisation, and the operator's control of them

**The stage's test is a sentence, and it is the owner's:** when it closes, everything about user
accounts, authentication, authorisation, admin user management and security is done and **fully
functional**. That last word is what makes the stage large. An audit on 11 Sep 2026 measured identity
at **71% built and 48% operational** — the difference being work that was built, is proven by tests,
and cannot be used by a real person: no email leaves the platform, because the only `EmailPort`
adapter writes verification links to the application log; no name is stored anywhere; the `otpauth://`
URI the API has returned since task 27.2 reaches the browser and is never drawn; an operator cannot
change their own password; a multi-membership account cannot switch organization; and an
organization can invite past any plan. None of that was identity debt in this file, because it was
filed under notifications, under operations, and under work found outside the plan.

**Twenty-nine numbers: sixteen existing groups and thirteen new ones (139–151).** Three batches, and
the batch is a sequence rather than a heading — a heading is something a commit message could cite,
and only task numbers may be cited.

**Batch A — the cascade gaps, and it is shorter than it was.** `82` (UX-80's dark map, whose own row
says retrofitting after twenty screens is the expensive path) and **`67.2`** (`pkg:ui` rather than
`admin`; `architecture.md` OQ-44 had to close before any console screen was built, or all six would
ship at the wrong density) both closed on 12 Sep 2026.

**Re-ordered the same day, on the project owner's observation that the batch had nothing to do with
identity.** The observation is correct and the original grouping was the author's. Batch A's argument
was *preconditions*, and it was sound for those two: both are cascade-level and every new screen
consumes them. It was never as strong for the other four, whose ordering force is **local** rather
than up front — `135` binds immediately before the six console screens, `133.1` immediately before
144/151 touch `manage-totp.use-case.ts`, and `137` and `102` bind nowhere in particular.
Front-loading them spent days before the stage's stated goal was touched, while identity sat at the
71%-built / 48%-operational split the stage exists to close. So they move to where they bind, and
**`96` moves up**: it is the one row of the four that *is* identity, and a live one — eight forms
carrying a credential or a one-time code put their fields in the URL when a submit beats hydration.

**The order from 12 Sep 2026 is therefore:** `96` → `51.1` (the SMTP adapter alone, ahead of the rest
of Batch C, because one adapter class and one `case` convert register, verify, forgot-password,
reset and invitations from built to usable) → Batch B's identity rows → the remainder of Batch C,
with `135` and `133.1` pulled in immediately before the work they precede and `102` and `137` taken
when they are cheapest.

**Batch B — identity completed:** 139 → 140 → 141 → 142 → 143 → 67.1 → 145 → 67.3 → 67.4 → 144 →
151 → 67.9 → 67.11 → 83 → 92 → 93 → 113 → 114. Two orderings inside it are load-bearing and are
stated on the rows themselves: **67.4 before 144**, or seven state-changing admin routes ship with no
`AuditInterceptor` to attribute them; and **145 before 67.3**, because the per-request lookup is what
`AdminRealmGuard` is built around.

**Batch C — notifications, and the accelerator over them:** 49 → 50 → 51 → 52 → 67.10 → 146 → 147 →
148 → 149 → 150. The whole notification subsystem is here rather than in a later stage because it is
the dependency closure of *a display name on a screen*: the only surface carrying a user's own
profile is S-27 (52.3), which also carries UC-168's preferences, which need 52.1 and 52.2, which need
49.1's category catalogue — and 51.1's SMTP adapter without 49.2 leaves the two mail paths that row
exists to prevent. Taking part of it would leave the mail subsystem half-built across a stage
boundary, which is this file's own definition of half a task.

**The accelerator is an amendment to the architecture, written before any of 146–150 is built.**
`architecture.md` §11.1 rejects a push transport by name and states the procedure — *"adding a push
transport is a deliberate change to §5.4 and §10.4, not an implementation detail"* — and **AD-15 is
that change**: a push accelerator over a polling floor, never an authority, citing AD-4 as precedent
because the architecture already runs exactly this pattern server-to-server. It carries **no new FR
and no new UC on purpose**: a requirement obliging the interface to reflect something without the
reader acting would rest a correctness obligation on a delivered frame, which is the one thing the
design refuses.

## Stage 9 — Advisor domain

**Appended 11 Sep 2026, when Advisor portfolio management was promoted out of `use_cases.md` §7.1 into MVP scope as
UC-196 … UC-211, FR-190 … FR-203, D-15 and D-16, with the `AD` actor registered in `actors.md`.**
Numbers are appended and the document's order is not the build order here: **task 116 lands with task 29 and must precede
every other row in this phase**, because the relationship is what the rest reads. Task 117 follows tasks 28 and 83, task 118
follows 83 and 32, task 119 follows 30, task 120 follows 53, 54, 63 and 68, and task 121 follows 49 … 52.
**What the promotion found, and it is why this phase is small rather than a second tenancy model.** The *provision* was
already MVP and only the *behaviour* was deferred: FR-14 models typed organization relationships expressly so the Advisor
type can be activated without a schema change, and FR-12 already resolves a caller's memberships and owns the switch of
active organization — **specified and scheduled as task 83, which is `TODO`**, and which the dependency line above already
makes 117 and 118 wait for. (This paragraph read *"task 83 built that switch three weeks ago"* when the phase was appended;
the global tier renders the organization as a plate precisely *because* that switch is task 83's and unbuilt — corrected
11 Sep 2026 before the rows were committed.) What had no row anywhere was the **relationship lifecycle**: a
request that confers nothing, a grant carrying an entity scope and an expiry, a revocation that bites on the next request.
Task 116 is that gap; everything after it is surface over it.
**Nothing here invents a parallel mechanism, and one row exists to prove it.** Entering a client (118.2) is task 83's switch
with membership resolved through a relationship rather than through a membership record — the same route, the same session
shape, the same `@RequiresRole` chain — which is a statement about the shape 83 will build rather than one about code that
exists, and is why 118 follows it. The consolidated board (118.3) reads task 42's roll-up rather than computing a second
one. The plan (120) is task 53's catalogue and task 54's entitlement service with advisor-scoped keys, and D-16 forbids any
of those keys reaching a client organization. The notices (121) are task 49's categories. A slice below that finds itself
needing a second mechanism has found a defect in task 116, not a requirement.
**D-15 is an architectural claim, and 117.2 is where it is tested rather than asserted.** An advisor session resolves to
exactly one tenant, so the RLS predicate and task 12's isolation proof apply unmodified and this phase introduces
**no exception to tenant isolation**. That is the whole distinction from the Corporate Buyer monitoring still deferred in
`use_cases.md` §7.1 — an advisor *enters* organizations one at a time, a buyer would *read across* them — and it is worth a
failing test rather than a paragraph.
