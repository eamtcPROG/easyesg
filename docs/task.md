# Tasks

The execution plan: the build order of [architecture.md](architecture.md) §15.4, sliced into
sequential tasks. Task *n+1* assumes task *n* is done. Tasks are **vertical slices in build
order, not per-application backlogs**: where a feature spans back and front, the API task comes
immediately before its screen task, so the sequence stays linear and every screen lands against
an API that already exists. Front and back are combined into one task only where splitting them
would produce fragments. The **Scope** column names the workspaces a task touches (`api`, `web`,
`admin`, `worker`, `pkg:*`, `infra`, `config`, `docs`, `root`); the UI track additionally
follows `design/IMPLEMENTATION_PLAN.md` on this same order.

**This is a tracking artifact, not an eighth specification document.** The seven-document set
keeps its precedence: where a task row and a spec identifier disagree, the identifier wins and
this row is what is wrong. Cite decisions by identifier (`FR-…`, `AD-…`, `DR-…`) rather than
restating them.

**Status:** `DONE` · `IN PROGRESS` · `TODO` · `BLOCKED`. Task numbers are stable — cite them in
commits and in [build-log.md](build-log.md), which records *how* each completed task actually
went, deviations included.

**A number is an identifier; only tasks 1–73 are also the order.** Those were sliced together and
each assumes its predecessor. Anything added afterwards is **appended, never inserted**: a task
number is cited in commit messages, in `architecture.md`, in `build-log.md`, in nine migration
files and in source comments, so renumbering would falsify every one of them and leave the stale
copies in git history wrong forever. The cost is that in the appended section the document's order
and the number's order differ — so each of those rows states where it actually lands, and a row
that must precede an earlier number says so in bold.

**A task too large to close in one go is split into sub-steps, never into new numbers.** Task 25
becomes `25.1`, `25.2`, `25.3`; the numbered row above them keeps its name, its description and its
recorded deferrals **verbatim**, and *task 25* still names the same body of work — so every citation
of it in `CLAUDE.md`, [build-log.md](build-log.md), `config/seed/README.md`, the migrations and some
forty source comments stays true. A sub-step is a **new identifier**, not a renumbering of anything,
which is the only reason the paragraph above permits it.

**Reading a split row.** A **bold number** is a group: its Description and Expected-result columns
are the original row, unchanged, and its Status is the roll-up of the sub-steps below it. A decimal
number is the executable unit — the thing someone picks up, closes, and writes a build-log entry
for. Where a sub-step's Scope differs from its parent's, the row says so and says why; that
correction is task 23's, made in its unknowns batch rather than discovered mid-build.

**A sub-step may be renumbered while nothing frozen cites it — and the renumbering is recorded.** Amended 25 Aug 2026, the first time it bit: task 36 went from four module slices to eleven, which shifted `36.3` … `36.7`. The rule above protects *history* — commit messages, migrations, source comments — and none of those named a `36.x`; the only citation was one row in this file, fixed in the same edit. Appending B4 as `36.8` would have obeyed the letter and destroyed the reading order of a task nobody has started. **The test is what a number is frozen into, not how old it is:** `25.4`, `51.1`, `51.4`, `52.3` and `60.4` are cited in commit `89781d7` and can no longer move, and a sub-step named in a build-log entry never moves again.

**A sub-step is sized to close on its own.** It passes `pnpm gates` and earns its own build-log
entry without waiting for its siblings — that is the whole test. A slice that cannot (a migration
without the use case that reads it, a screen without its API) is not a sub-step but half of one, and
belongs merged with its other half. Where a sub-step's unknowns differ from its parent's, they are
named in its row and raised in its own batch.

**Split 25 Aug 2026, and the evidence was already in the build log.** Task 23 shipped and then
needed **three addenda**; tasks 20 and 24 needed one each. An addendum is a task that was declared
closed and was not, and every one of them landed on a row carrying three or more independent
deliverables. Tasks 1–24 are left exactly as they were: they are `DONE`, and their history is what
it is.

**Before starting a task, raise its unknowns in one batch** (CLAUDE.md, "Open questions are not
debt"). A task is not started by writing its first file; it is started by checking what it needs
decided.

**Before closing one, run `pnpm gates` — and `pnpm gates:clean` before pushing** (CLAUDE.md,
"Closing a task"). The clean run is what catches a gate depending on state a previous command left
behind, which an incrementally-built tree hides completely. Then write the build-log entry: a task
whose reasons are not recorded is not closed.
