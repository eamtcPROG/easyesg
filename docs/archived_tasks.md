# Archived tasks

The closed half of the execution plan: **105 task numbers, 207 rows**, filed under the phase
headings they were sliced and closed under. [task.md](task.md) holds what is left; this file holds
what is done, so that neither has to be read through to answer the other's question.

**This is a tracking artifact, not an eighth specification document.** The seven-document set keeps
its precedence: where a task row and a spec identifier disagree, the identifier wins and this row is
what is wrong. Nothing here owns a decision, and a row is never amended to record one — the document
that owns it is amended instead.

**A number is an identifier, never re-used and never renumbered, and this file is what a citation
resolves against.** A task number is cited in commit messages, in `architecture.md` §12.5.6, in
[build-log.md](build-log.md), in thirty-four of the thirty-six migration docblocks and in several
hundred source comments. Closing a task moved its row here; it did not retire its number. A reader
who meets *task 27.1* in a migration written a year ago finds it here, with the text it had.

**The phase headings are `architecture.md` §15.4's build order as the plan was first sliced, and
§15.4 is unamended.** They are not the order the remaining work will be delivered in — [task.md](task.md)
carries that, as an independent Stage sequence — which is why §15.4's steps 4 through 9 have no
section here: nothing under them has closed yet. A heading with no rows would claim otherwise, so
the empty ones are omitted rather than carried.

**Why a row ended up as it did is in [build-log.md](build-log.md)**, whose entries are headed
`## Task N — …`; search for `## Task N`. A sub-step's reasons sit in its parent's entry unless it
closed on its own, in which case it has its own heading, and some entries span several numbers and
say so in their heading. There is deliberately no link column here: 150 anchors would re-encode each
heading's name and date a second time and break silently the first time one is edited.

**Tasks 82 and 83 sit in the appended section although their numbers are below 85**, and for the reason that section exists. Task 83 was appended on 29 Aug 2026, split out of task 30.1, and its number is an identifier rather than a position. Task 82: it was appended on 26 Aug 2026 and landed under *Phase 10 — Comprehensive Module* by the same accident 85–115 did. Filing it under a Phase 10 heading here would make that phase read as having closed something when none of tasks 78–81 has started — which is precisely the misreading the heading split was made to end.

**Two reading-order changes were made in the move, and no number moved.** Task 91's group read
`91, 91.1, 91.2, 91.3, 92, 93, 91.4` — `91.4` having been appended after 92 and 93 — so moving 91 as
a group rejoins `91.4` with its siblings while 92 and 93 stay in [task.md](task.md). And the two
appended sections are ordered here by their numbers rather than by where they sat in the source
file, which is what finally makes *(continued)* accurate: 85–115 first, 122–138 after it.
